# Журнал прогонов бенчмарка LLM (ипотека, df_mortgage)

Правило: **одно изменение — один прогон — весь корпус (8 ипотечных файлов) —
скорость и качество в одной строке**. Два изменения в одном прогоне не
объединяются, даже если оба «очевидно помогают»: трижды уже получали регресс
там, где ожидали улучшение (handoff §R.9, §R.15, §R.17).

Команда прогона (из `python-backend/tests`, venv конвертера — там llama-cpp):

```
../../converter/.venv/Scripts/python.exe -u llm_bench_run_fields.py \
  --model ../../converter/models/gemma-3-4b-it-Q4_K_M.gguf \
  --prompt df_mortgage --label <метка> \
  --dump llm_bench_dump_debtorfields_full66.json \
  --n-ctx 8192 --n-threads 8
```

Сверка качества (без LLM):

```
../venv/Scripts/python.exe llm_bench_rescore.py --in llm_bench_results_<метка>.json \
  --baseline llm_bench_results_<эталон>.json --calls
```

**Гигиена замера.** Тайминг мерить только на незанятой машине: любой
параллельный процесс (второй прогон, тяжёлый python, сборка) искажает цифру в
разы. Сон/гибернация машины во время прогона тоже попадает в `elapsed_sec` —
такой прогон по времени недействителен (по качеству остаётся валидным).

## Отзывчивость ПК под фоновым инференсом (замеры отложены на после этапов 5-6)

Вопрос Андрея по ходу работы: прогон занимает до 93% CPU на мощной машине — что
будет у пользователя со слабой, когда он параллельно работает в других
программах. Разбор:

- Потоки llama.cpp работают на **busy-wait**: не спят в ожидании, а жгут ядро.
  `n_threads=8` на 8 физических ядрах — это занятость всех ядер, а не «половина
  логических».
- Рывки интерфейса всего ПК дают не загрузка сама по себе, а **равный
  приоритет**: планировщик даёт нашим потокам столько же, сколько потоку
  прокрутки браузера.
- Масштабирование почти линейно по ядрам: 8 ядер ~205с/файл, 4 ядра ~400с,
  2 ядра ~800с.
- Память: ~2.5 ГБ резидентно (Q4_K_M 4B) + KV-кеш. На машине с 8 ГБ вместе с
  Electron это грань свопа, а своп превращает «медленно» в «встало».

Принято в код сразу (умолчания, без замеров — замеры после этапов 5-6):

1. `physical_cores()` теперь `физические − 1`. **Был баг**: прежний зажим
   `max(4, ...)` на 2-ядерной машине просил 4 потока — ровно та переподписка,
   от которой функция должна защищать.
2. `lower_process_priority()` + флаг `--low-priority`: ниже обычного через
   ctypes (Windows) / `os.nice(10)` (Unix), без psutil — его нет в зависимостях
   backend'а. На простаивающей машине плата по скорости близка к нулю, при
   работе пользователя ОС вытесняет нас мгновенно. По умолчанию ВЫКЛЮЧЕНО,
   чтобы не сбить сопоставимость замеров скорости с базой.
3. Архитектурно уже покрыто решением про сайдкар: инференс в отдельном процессе
   → понижается в приоритете целиком, убивается в любой момент, выгружается по
   сторожу простоя (механизм для конвертера уже написан).

Открытый вывод для прод-интеграции: на слабой машине синхронного режима быть не
может в принципе (400-800с ожидания — это неработающая программа). Асинхронность
из желательной становится обязательной, а на совсем слабых машинах правильное
поведение — не включать LLM-слой вообще, определяя это по числу ядер и объёму
ОЗУ при старте.

## Этап 4b — детали (принят)

Кешируется НЕ документ, а префикс промпта (system + few-shot): 2258 токенов у
основного вызова одинаковы для всех документов. Поэтому первый файл платит
полную цену (164.2с, кеш пуст), а последующие идут по 67-146с. В проде это
значит: выигрыш начинается со ВТОРОГО документа подряд, а первый лечится
прогревом (прогнать четыре префикса вхолостую сразу после загрузки модели,
~35с однократно) или `LlamaDiskCache` — он переживает перезапуск процесса, и
`diskcache` уже лежит в офлайн-комплекте конвертера.

prefill по вызовам: main 48.2 → **20.2с**, collateral 17.0 → 7.8с,
valuation 14.5 → 5.0с. Суммарно 82.2 → **34.6с**.

**Цена — недетерминизм.** Восстановление KV меняет границы батчей, и в спорном
месте жадный выбор токена падает в другую сторону. Конкретный ущерб на корпусе —
ОДНА фамилия в одном файле (БИЦИЕВ): `Жевнин` → `Жевнинов`. Адрес того же
должника при этом идентичен символ в символ, он «просел» только как каскад:
`_match_array` пары строит по имени, имя не совпало — вся запись не спарилась.
То есть из двух потерянных очков метрики реальное одно.

Для теневого слоя цена ошибки — одна лишняя ложная тревога («разбор дал Жевнин,
LLM нашла Жевнинов»), данные не портятся, автоподстановки нет.

**Не замерено:** RSS во время прогона вернулся 0 — в `process_rss_mb()` не были
объявлены типы ctypes, и 64-битный HANDLE усекался (вызов молча возвращал 0).
Починено; расчётная цена кеша ~0.9 ГБ, фактическая будет в следующем прогоне.

## Память — замерено прицельно (приватная память процесса)

| конфигурация | после загрузки | после 3 файлов | прирост |
|---|---|---|---|
| `n_ctx=8192`, без кеша | 4248 МБ | 4279 МБ | 32 МБ |
| `n_ctx=8192`, кеш | 4249 МБ | 6960 МБ | **2711 МБ** |
| `n_ctx=4096`, кеш | 3701 МБ | 6410 МБ | 2708 МБ |

**Штатный `LlamaRAMCache` для прода не годится.** Его ключ — промпт ПЛЮС ответ,
то есть в ключ входит текст документа: кеш кладёт отдельное состояние на КАЖДЫЙ
документ, а не одно на шаблон промпта. За рабочий день он упрётся в лимит и
начнёт вытеснять по LRU. Нужен прогрев ТОЛЬКО префиксом — одно состояние на тип
вызова, четыре штуки, без роста от числа документов.

`n_ctx` 8192 → 4096 экономит 548 МБ и теперь безопасен (промпт ужался с 6100 до
~3000 токенов, запас до переполнения больше не критичен) — это отложенный шаг 3d.

## Главные кандидаты следующей итерации

1. **Пакетный режим (continuous batching).** Четыре вызова идут строго
   последовательно. Параллелить их отдельными контекстами на CPU бессмысленно
   (ядра уже заняты, узкое место — пропускная способность памяти, что и показал
   провал `n_batch`). Но подать четыре последовательности в ОДИН forward-проход
   выгодно принципиально: на каждый токен читаются все 2.3 ГБ весов, а
   арифметика простаивает — при пакете веса читаются один раз на четыре токена.
   При нынешнем decode 69с из 104с это крупнейший оставшийся рычаг. Цена:
   параметром не выставляется, нужен `llama-server` со слотами или
   низкоуровневый batch-API.
2. **Прогрев кеша только префиксом** (вместо штатного кеша, см. выше).
3. **Квантование Q3_K_M** — decode упирается в объём весов, меньше байт →
   быстрее, ориентировочно −25%. Риск по качеству прямой, нужен полный гейт.
4. **5c, компактный JSON** — до −10с, но сначала переделать построчный
   `_repair_json`, иначе ремонт битого JSON перестанет работать.

## Пакетный режим (continuous batching) — ПРОВЕРЕН ПРОТОТИПОМ, ОТКЛОНЁН

Гипотеза: decode упирается в чтение весов (2.3 ГБ на токен), арифметика
простаивает — значит четыре секвенции в одном forward-проходе читают веса раз
вместо четырёх. Ожидали до 4×.

Прототип (`scratchpad/batch_probe.py`, низкий уровень: свой контекст с
`n_seq_max`, свой батч, жадный выбор через numpy):

| секвенций | decode суммарно |
|---|---|
| 1 | 13.75 ток/с |
| 4 | 27.63 ток/с |

**Фактически 2.0×, а не 4×.** Плюс неравная длина ответов (446/236/82/19
токенов) убивает вторую половину выигрыша: последние 210 шагов основной вызов
доделывает в одиночку. По замеренной стоимости шага — 41с против 57с, то есть
в пересчёте на бенчмарк 104с → ~84с (**−19%**).

Цена: высокоуровневый `Llama` многосеквенционную генерацию не поддерживает
(`n_seq_max>1` ставится только в режиме эмбеддингов), нужен полный переписанный
цикл генерации на низком уровне — шаблон чата, токенизация, батч, жадный выбор
по секвенциям, EOS/стоп, сборка многобайтового UTF-8, плюс посеквенционные
состояния (`llama_state_seq_get_data`/`set_data` — в биндингах есть) ради
сохранения кеша префикса.

**Вывод: несколько часов работы и отказ от протестированного кода ради 20
секунд — не окупается.** Полчаса прототипа сэкономили эти часы.

Следующий по величине кандидат — **квантование Q3_K_M**: decode упирается в
объём весов, минус четверть байт даёт минус время И на decode, И на prefill
(порядка 25-30с), причём это не переписывание кода, а другой файл модели плюс
прогон с гейтом. Риск по качеству прямой: бюджет невелик (89.4%,
`debtors.inn` уже 73%).

## Спекулятивное декодирование (prompt lookup) — ОТКЛОНЕНО

Гипотеза была сильной: наша выдача — почти дословное копирование из входа
(ФИО, ИНН, адреса, кадастровые номера), значит черновик угадывается прямо из
промпта без второй модели. И приём ТОЧНЫЙ: предложения проверяются полной
моделью, результат обязан совпасть с обычной генерацией.

В llama-cpp это встроено: `LlamaPromptLookupDecoding` + параметр `draft_model`.

**Первый запуск упал**: `could not broadcast input array from shape (134217728,)
into shape (0,)`. 134217728 = 512 x 262144 = `n_batch` x словарь. Причина — баг
библиотеки: при `draft_model` она принудительно ставит `self._logits_all=True`
(llama.py:344), но буфер логитов выделяет по ПАРАМЕТРУ `logits_all`
(llama.py:475). Обход — выставить параметр явно, ценой буфера
`n_ctx x 262144 x 4` байта: 4.3 ГБ при n_ctx=4096, 8.6 ГБ при 8192.

**Результат после обхода — провал по всем статьям:**

| | база (stage5a) | спекуляция |
|---|---|---|
| decode | 11.3 ток/с | **10.9 ток/с** |
| prefill | 82.2с (без кеша) | 89.0с |
| качество | 193/216 | **158/216** |
| валидный JSON | 8/8 | 7/8 |

Ускорения decode НЕТ вообще, prefill потяжелел от `logits_all`, качество
обвалилось. Реализация в этой версии обвязки нерабочая. Флаг `--draft-lookup`
оставлен (по умолчанию 0, поведение не меняет) как задокументированный
отрицательный результат.

## `n_threads_batch` — ОТКЛОНЕНО, и вывод обратный ожидаемому

Находка в коде: llama-cpp ставит `n_threads_batch` = число ЛОГИЧЕСКИХ ядер
(llama.py:306), то есть 16, хотя мы задаём `n_threads=8`. Выглядело как
незамеченная переподписка по гиперпоточности в prefill.

Замер: первый файл **201.1с против 159.7с** — явный регресс, прогон остановлен.

**Гиперпоточность prefill'у ПОМОГАЕТ.** Логично: prefill упирается в
арифметику (в отличие от decode, который упирается в память), и лишние
логические потоки загружают простаивающие блоки процессора. Умолчание
библиотеки верное, трогать не надо. Флаг `--n-threads-batch` оставлен
(0 = как есть).

## Компактный JSON грамматикой — замер объёма потерь

Модель выдаёт JSON С ОТСТУПАМИ и переносами строк плюс markdown-обёртку, хотя
few-shot однострочный (`json.dumps` без indent) — она его игнорирует, так
обучена. Уговаривать текстом бессмысленно.

Замерено токенайзером по сохранённым ответам, на файл:

| вызов | сейчас | компактно | потери |
|---|---|---|---|
| main | 446 | 333 | **113** |
| collateral | 236 | 222 | 14 |
| valuation | 82 | 70 | 13 |
| rep_plaintiff | 19 | 13 | 6 |
| **ИТОГО** | **783** | **637** | **146 ток = 13с** |

12.5% времени уходит на пробелы. Решение детерминированное — GBNF-грамматика
(`_COMPACT_JSON_GBNF`), которая ограничивает САМ ВЫБОР токена: пробел физически
не может быть выбран. Это не промпт-хак, риска whack-a-mole нет.

## Компактный JSON грамматикой — ОТКЛОНЕНО (замедление в 2-3 раза)

Первая попытка дала 0 токенов на всех 8 файлах: грамматика была синтаксически
битой (ошибка экранирования кавычки — в GBNF это `"\""`), а
`LlamaGrammar.from_string(verbose=False)` **проглотил это молча**, без

ДО прогона корпуса.

После починки грамматика работает верно —
`{"name":"Иванов Иван Иванович","inn":"231552257675"}`, ни переносов строк, ни
markdown-обёртки. Но время:

|---|---|---|

Прогон остановлен на 5 файлах. Причина: на КАЖДОМ шаге генерации грамматика
фильтрует весь словарь — 262144 токена. Мы экономим 146 токенов, но каждый из
оставшихся ~640 дорожает многократно. Экономия 13с против расхода в сотни.

**Это было известно и раньше**, просто записано как вывод про качество:
handoff §R.1 — «grammar-режим нигде не улучшил качество ни у одной из 7
моделей, только тратил время». Стоило взвесить эту фразу сразу.

Флаг `--compact-json` оставлен (по умолчанию выключен) как задокументированный
отрицательный результат вместе с рабочей грамматикой — она может пригодиться
там, где нужен гарантированно валидный JSON, а не скорость.

## Отпечаток корпуса — обязателен в каждой записи (введён 2026-08-20)

Корпус заявлений лежит ВНЕ репозитория и меняется. Один раз это уже испортило
серию замеров: в файл корпуса вставили строку-мусор посреди прогонов, и цифры
двух соседних записей оказались несравнимы — заметить это удалось только на
глаз, задним числом.

Теперь `llm_bench_run_fields.py` печатает отпечаток сразу после загрузки дампа
и повторяет его в шапке отчёта:

```
Корпус: 66 файлов, a9fb060fe6b9
```

Считается по ОКНАМ, которые реально видит модель (`header_window`,
`prayer_window`, `collateral_block`, `valuation_block`), а не по файлам на
диске. Правка документа за пределами окна на результат не влияет, и объявлять
из-за неё замеры несравнимыми было бы ложной тревогой. Правку одного символа
внутри окна отпечаток ловит.

**Правило: записи с разными отпечатками сравнивать нельзя.** Не совпало —
сначала объясни почему, потом уже смотри на цифры.
